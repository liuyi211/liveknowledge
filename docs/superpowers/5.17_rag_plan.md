# RAG Pipeline 补全计划 — 2026-05-17

> **执行时机**：MVP 全部完成后（Task 0~16 结束），作为 v0.1.x 补丁批次实施。
> **原则**：增量补全，每步可独立验证；先补齐检索质量，再上图谱和缓存。

---

## 现状速览

| 组件 | 当前状态 | 缺失程度 |
|------|----------|----------|
| Query Rewrite | 基础 LLM 改写（去口语化） | 缺 HyDE、子查询分解、关键词提取、共指消解 |
| 向量检索 | pgvector HNSW cosine，可用 | 缺 ef_search 调参、metadata 过滤 |
| 全文检索 | 客户端 LIKE 过滤（伪全文） | **缺 tsvector + ts_rank + 中文分词** |
| 图谱检索 | 完全未实现 | **缺 Neo4j 关联查询** |
| 结果融合 | 简单去重取最高 similarity | **缺 RRF（Reciprocal Rank Fusion）** |
| 重排序 | 未实现 | **缺轻量 LLM 重排序** |
| 上下文组装 | 固定截断 1000 字 | **缺动态预算分配、会话级缓存** |

## Step 1: PostgreSQL 全文检索（tsvector）

**目标**：替换客户端 LIKE 过滤，实现真正的数据库级全文检索。

**改动点**：
- `backend/src/db/schema.ts`: 为 `notes` 表添加 `searchVector` 字段（tsvector）
- 创建 GIN 索引 `idx_notes_search`
- 添加触发器/自动更新函数：note 插入/更新时自动维护 searchVector
- `backend/src/services/rag.ts`: `retrieveFullText` 改为 `ts_rank` SQL 查询

**权重策略**：title 权重 A > content 权重 B > tags 权重 C。

**中文分词方案**：
- 首选：`pg_jieba` 扩展（结巴分词）
- 备选：按字切分 + 前缀匹配（如果 pg_jieba 安装复杂）

**验收**：搜索"线性代数"能命中标题含"线性代数"的笔记，且排名高于正文仅提及的笔记。

---

## Step 2: RRF 多路融合

**目标**：用 Reciprocal Rank Fusion 替代当前简单去重，让向量+全文结果科学融合。

**改动点**：
- `backend/src/services/rag.ts`: 新增 `reciprocalRankFusion()` 函数
- 公式：`score = Σ(1 / (k + rank))`，k 默认 60
- 三路输入：向量 TOP-10、全文 TOP-10、图谱 TOP-10（可选）
- 输出：融合后 TOP-20

**验收**：同一 sourceId 在向量排第 3、全文排第 5，融合后分数高于仅在向量排第 2 的结果。

---

## Step 3: 轻量 LLM 重排序

**目标**：对融合后的 TOP-20 精排，取 TOP-5 作为最终上下文，提升相关性。

**改动点**：
- `backend/src/services/rag.ts`: 新增 `rerankChunks()` 函数
- Prompt："判断文档片段是否能帮助回答用户问题，输出 0-10 分"
- 模型：gpt-4o-mini / glm-4-flash（轻量、低成本）
- 并发：20 个请求并行
- 成本预估：20 次调用 ≈ ¥0.02-0.06/请求

**验收**：输入一个明显无关的笔记片段，重排序分数 < 3；输入直接相关的片段，分数 > 7。

---

## Step 4: Query Rewrite 增强

**目标**：从简单改写升级到结构化的多策略改写。

**改动点**：
- 输出 JSON 格式：`{ rewritten_query, keywords, sub_queries, intent }`
- 新增 **HyDE（Hypothetical Document Embeddings）**：
  - 场景：用户问题简短/模糊
  - 流程：LLM 生成假设答案 → embedding → 向量检索
- 新增 **子查询分解**：多条件问题拆分为独立子查询
- 新增 **共指消解**（v0.1.x 可选，可延后）：维护会话已提及实体列表

**改动文件**：
- `backend/src/services/rag.ts`: `rewriteQuery()` 重构
- 可能需要新增 `backend/src/services/query-rewrite.ts`

**验收**：输入"给我讲讲这个"（在"线性代数"会话中），改写为"请解释线性代数的核心概念"。

---

## Step 5: 图谱检索增强（Neo4j）

**目标**：基于向量检索结果查询 Neo4j 关联节点，扩展候选池。

**改动点**：
- 新建 `backend/src/services/graph.ts`: Neo4j 连接 + 查询封装
- 触发条件：向量检索有结果时才激活图谱扩展（避免空查）
- Cypher 查询：从向量结果中的 concept 节点出发，查询 1-2 跳邻居
- 合并：关联节点的对应笔记/chunk 合并到向量候选池（去重）

**Cypher 示例**：
```cypher
MATCH (c:Concept)
WHERE c.label CONTAINS $topic
MATCH (c)-[r:RELATED_TO|PREREQUISITE_OF|IS_A|PART_OF]-(related)
RETURN c.label as source, related.label as target, type(r) as relation
LIMIT 10
```

**验收**：查询"矩阵运算"时，向量检索命中"矩阵乘法"笔记，图谱扩展额外带回"线性代数"基础概念。

---

## Step 6: 会话级检索缓存与去重

**目标**：同一对话内避免重复注入相同 chunk，减少 token 浪费。

**改动点**：
- `backend/src/services/rag.ts`: 新增 `SessionRetrievalCache` 类
- 缓存：同一会话最近 N 轮检索结果
- 去重：同一 source_id 只保留 similarity 最高的 chunk
- 失效：会话结束时清除（或按时间 TTL）

**数据结构**：
```typescript
interface SessionRetrievalCache {
  sessionId: string;
  recentResults: Array<{ query: string; chunks: Chunk[]; timestamp: Date }>;
  injectedChunkIds: Set<string>;
}
```

**验收**：连续两轮对话检索到同一笔记的不同 chunk，第二轮只注入未出现过的 chunk。

---

## Step 7: 动态上下文预算分配

**目标**：根据模型 context window 和历史消息长度，自适应分配检索上下文预算。

**改动点**：
- `backend/src/services/rag.ts`: 新增 `allocateContextBudget()` 函数
- 公式：
  - totalBudget = modelConfig.context_window * 0.9（留 10% 缓冲）
  - reserved = systemPrompt + userInput + 500（响应预留）
  - available = totalBudget - reserved
  - retrievalBudget = max(1500, available * 0.35)
- 如果历史消息很少，剩余预算分配给检索

**改动文件**：
- `backend/src/services/rag.ts`
- `backend/src/routes/messages.ts`: 在组装 system prompt 前调用预算分配

**验收**：gpt-4o-mini（128K）和 moonshot-v1-8k（8K）在同一会话下，检索上下文 budget 不同。

---

## Step 8: 向量检索调优

**目标**：HNSW 参数调优 + metadata 过滤支持。

**改动点**：
- 数据库：确认 HNSW 索引参数 `m=16, ef_construction=64`
- 查询时：`SET hnsw.ef_search = 100`
- metadata 过滤：按标签、source_type 过滤（如只检索 notes，不检索 conversations）

**验收**：带 tag 过滤的检索比全量检索快且结果更精准。

## 风险与备选

| 风险 | 影响 | 备选方案 |
|------|------|----------|
| pg_jieba 安装失败 | 中文全文检索不可用 | 按字切分 + 前缀匹配 |
| Neo4j 未就绪 | 图谱检索不可用 | 跳过 Step 5，等 Neo4j 数据积累后再上 |
| LLM 重排序成本高 | 延迟/费用增加 | 降级为本地 cross-encoder（需额外模型文件） |
| 改写 LLM 调用失败 | 检索质量下降 | fallback 到原始 query |

## 验收总标准

补全后的 RAG pipeline 应能通过以下测试场景：

1. **中文语义检索**：输入"怎么算行列式"，命中标题为"行列式计算方法"的笔记（向量检索）
2. **中文关键词检索**：输入"行列式"，命中正文多次提及"行列式"的笔记（全文检索）
3. **融合去重**：同一笔记同时被向量+全文命中，结果只出现一次，similarity 取最高
4. **重排序过滤**：融合结果中混入一条明显无关的笔记，重排序后该笔记被挤出 TOP-5
5. **上下文长度控制**：使用 8K 模型时，检索上下文不超过 1500 tokens；使用 128K 模型时，检索上下文可扩展
